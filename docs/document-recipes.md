# 用现有规则配置单据数据

[English](document-recipes.en.md)

faker-data 是通用的关系数据生成器。业务表名、字段名、状态值和关联规则由使用者的配置决定，产品不内置特定公司的单据模型或工作流。AI 应先读取目标元数据与业务约束，再把需求转换成现有规则和可复用方案。

## 已验证的通用配置

[请求 JSON](../examples/generate-document-states.json) 和 [MySQL 示例表结构](../examples/mysql-document-schema.sql) 演示一次生成：

- `demo_document`：170 张单据，精确包含 `SAVED` 50 张、`SUBMITTED` 20 张、`APPROVED` 100 张。
- `demo_document_extension`：170 条扩展记录，与主表逐行共用同一个主键。
- `demo_document_line`：340 条明细，每张单据恰好 2 条，每条金额 12.50，合计等于主表金额 25.00。
- 明细中的 `document_state` 和扩展表中的 `state_copy` 均引用所关联主记录的状态，保持同一条父记录的各字段一致。

这些英文状态是示例表的普通字符串，不是通用审批协议。此示例验证数据行、数量、关联和金额一致性；不创建真实工作流实例、待办或审批记录，也不证明其他业务系统可以执行提交、审批等动作。

配置只使用已有规则，没有新增业务适配代码：

| 需求 | 配置方法 | 适用边界 |
| --- | --- | --- |
| 唯一主键 | `FIX.UUID` | 不替代目标业务系统的专有编号机制 |
| 单据号 | 常量 `DOC-` 拼接 `REF.SELF_COLUMN` 引用序号 | 序号每次任务重置，需要按实际唯一约束调整 |
| 精确状态数量 | 序号从 1 递增，`COND.EXPR` 以 `between(#sequence_no,1,50)` 分段 | 权重候选是随机选择，不能保证精确 50/20/100 |
| 共享主键的扩展表 | `REF.OTHER_TABLE` 引用主表 `id`，表数量同为 170 | 当前按生成行序对齐 |
| 每个主记录 2 条明细 | 明细数量设为父表数量的 2 倍 | 引用按行号取模循环，不代表支持任意父子数量策略 |
| 跨表多字段一致 | 明细同时引用主表 `id` 和 `state` | 相同父表的字段使用同一被引用行 |
| 金额一致 | 明细金额固定 12.50，主表固定 25.00 | 这是预先一致的常量，不是引擎对子表求和 |

## AI 如何执行

1. 确认用户授权的目标库及写入范围。在独立测试库中按需执行示例 DDL；生成 API 本身不建表。
2. 通过 `/db/showTables`、`/db/showColumns/{table}` 读取实际字段元数据。对于自己的业务表，保留元数据中的类型、长度、可空性；示例 JSON 只适用于附带的示例表。
3. 配置目标连接，并为本次运行替换 JSON 中的 `DOC-DEMO-CHANGE-ME` 标识。密码通过本地 `FAKER_TARGET_PASSWORD` 环境变量提供，不提交到仓库。此标识只便于定位，不提供幂等或自动清理能力。
4. 按 [AI 调用指南](../AI_USAGE.md) 使用同一条 `GEN_DATA` 接口。也可以使用现成客户端：

   ```sh
   python examples/ai_client.py --request examples/generate-document-states.json
   python examples/ai_client.py --request examples/generate-document-states.json --submit --timeout 300
   ```

   第一条只检查连接并读取元数据；第二条才提交生成任务。提交超时后先核对原任务和目标记录，不自动重试。

5. 查询同一个任务 UUID，等待 `FINISHED` 且进度为 100。再用单独获授权的数据库查询工具检查状态计数、孤儿明细、每单明细数量和金额合计。API 没有任意 SQL 查询或批次清理接口。
6. 需要复用时，将 `{name,dataSource,tables}` 保存到 `/scheme/save`；方案只保存配置，不代表已生成或验证业务数据。方案会把连接凭据存到本机，注意本地文件权限。

状态字段对应哪些列表页签、详情需要哪些关联表、保存单能否提交，都必须按目标系统实际规则另行验证。

## 当前能力与缺口

| 场景要求 | 当前能力 | 后续通用能力候选 |
| --- | --- | --- |
| 固定数量的主子表和多种状态 | 现有规则可表达，上述配置已做本地集成测试 | 先复用现有配置 |
| 引用现有用户、组织、流程定义等数据 | 当前源码新增 `existingData`，一次读取受限候选集，整行引用 | 详见[已有数据引用](existing-data.md)，尚未发布到旧版 JAR |
| 只为 `SUBMITTED` 父记录生成子行 | 当前源码新增 `parentRows`，按父字段筛选、固定数量展开 | 只生成行，不代替流程引擎创建待办 |
| 每单不同明细数量、每个审批节点一行 | 可按父记录固定数量展开；不自动解析流程定义 | 可变数量、逐父编号及按已有节点集合展开尚未实现 |
| 主表金额随明细求和 | 当前没有跨行聚合规则；可先用一致常量 | 跨表聚合、生成后约束校验 |
| 按已有流程定义创建可继续审批的运行实例 | 现有引擎只插入支持类型的字段；不能执行状态机或构造专有序列化运行态 | 先验证具体系统需要的数据协议；不能用状态字段冒充真实执行 |
| 本次数据完整追踪与安全撤销 | 当前无生成批次清单与自动撤销 | 通用批次主键清单、依赖检查和受限清理 |

表中明确标注的 `existingData` 与固定数量 `parentRows` 已在当前源码实现；其余候选尚未实现。新增能力通过配置表达差异，不在核心代码写入特定系统的表名、接口或审批规则。真正的工作流可操作性仍需独立验证，不能由插表成功推断。

本地测试使用临时 H2 数据库及真实生成引擎；没有连接外部业务系统。实际目标数据库与应用的业务验收需要另行执行。
